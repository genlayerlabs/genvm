# ADR-011: Runner IDs and Runtime Runner Registration

## Status

- **Status**: Accepted
- **Date**: 2026-06-19

## Context

[ADR-002](<002. code loading.md>) introduced runners and identified them by a
`<human-readable-id>:<hash>` string, with a special `<contract>` literal for the
contract currently being executed and an internal `on_chain:0x<address>` id used
when loading a contract's own runner from its code.

This scheme is limiting:

- The `<contract>` literal and the `on_chain:` id were implementation details
  that were never specified, so contracts could not reference runner code stored
  on chain in a documented, stable way.
- There is no way to load runner code from an arbitrary contract's storage, which
  blocks reuse of code parts between contracts (see research
  [GVM-231](https://linear.app/genlayer-labs/issue/GVM-231)).
- There is no way for a contract to provide runner code at runtime (e.g. to build
  a more capable / user-provided execution environment) — the runner set was
  fixed at load time.

## Decision

Rework runner ids into four explicit, specified forms (parsed in
`executor/src/runners`):

1. `name:hash` — a packaged runner by human readable name (`[a-zA-Z0-9_-]+`) and
   archive hash. In debug mode the hash may be `test`/`latest`. Unchanged.
2. `contract` — the runner of the contract currently being executed. Replaces the
   old, undocumented `<contract>` literal.
3. `chain:<address>[:<a|f>[:<slot>]]` — load a runner code blob directly from a
   storage slot of an arbitrary contract: `<address>` is a `0x` 20 byte hex
   address, `a`/`f` selects accepted (latest non final) / finalized state, and
   `<slot>` is a 32 byte slot id encoded with GVM32 (Crockford Base32, not `0x`
   hex). Both `<a|f>` and `<slot>` are optional: `<a|f>` defaults to `a` and
   `<slot>` defaults to the target contract's resolved root code slot, so
   `chain:<address>` and `chain:<address>:a` are valid shorthands. The current
   contract's runner is the canonical `chain:` id pointing at itself and the code
   slot, so `contract` and an explicit self reference deduplicate in the cache.
4. `custom:<hash>` — a runner registered at runtime, looked up in an in-memory map
   keyed by `<hash>` (the GVM32-encoded SHA3-256 of the registered code).

`contract`, `chain` and `custom` are reserved prefixes and cannot be used as
human readable runner names.

Add a `gl_call` `RegisterRunner { code: Bytes }` that parses `code` as a runner
archive, charges its size against the memory limit and stores it under
`custom:<hash>`, where `<hash>` is the GVM32-encoded SHA3-256 of `code`. It
returns the resulting runner id. It is allowed only in deterministic mode and only when the contract
holds the new `register_runners` permission (permission char `u`). A friendly
`genlayer.vm.register_runner(code) -> str` wrapper is exposed in the Python SDK.

Add a companion `gl_call` `MapFile { runner, path_in_runner, path_in_vfs }` that maps
a file (or, when `path_in_runner` ends with `/`, a directory subtree) from any
runner into the VM filesystem at runtime, sharing the exact logic of the `MapFile`
runner action. Because resolving a `chain:` runner reads another contract's
storage, it requires the `read_storage` permission. Exposed as
`genlayer.vm.map_file(...)` in the Python SDK.

## Consequences

### Positive

- Runner ids are fully specified and uniform; `contract`/`chain`/`custom` are
  first-class instead of hidden literals.
- Contracts can load code parts from other contracts' storage on chain.
- Contracts can extend their execution environment with runtime-provided code.

### Negative

- `<contract>` is no longer accepted; runners embedding it must be rebuilt to use
  `contract` (done for the bundled `py-genlayer` wrappers).
- `chain` and `custom` become reserved prefixes, slightly shrinking the space of
  valid human readable runner names.

### Neutral

- The `custom:` map is per-execution and starts empty; registered runners do not
  persist across executions.

## Alternatives Considered

- **Keep `<contract>`/`on_chain:` internal-only**: rejected because contracts
  need a documented way to reference on-chain and current-contract runners.
- **A dedicated `exec` gl_call that replaces the current VM with a new one
  carrying user code** (GVM-231 idea A): rejected for now because propagating the
  extended runner into sub-sub-VMs is not obvious; registering under `custom:` and
  referencing it from ordinary `Depends`/`With` composes with the existing loader.

## Implementation Notes

- Parsing/canonicalization lives in `executor/src/runners/mod.rs`
  (`parse_runner_id`, `chain_canonical`, `custom_runner_hash`); resolution and
  loading in `executor/src/rt/supervisor/actions.rs`.
- `chain:` reads code via a fresh `Storage` pointed at the target address/state
  and `read_code_at(slot)`.
- A dependency whose runner declares a public-ABI major different from the host's
  `CURRENT_MAJOR` is rejected before its code is loaded, so an incompatible
  on-chain runner cannot be pulled in via `Depends`/`With`.
- Runner ids are interned via a `StrSymbol` newtype so the runner maps stay
  interned while lookups accept `&str` without interning untrusted input (an
  attacker-supplied id cannot grow the global symbol table).
- The `custom:` map lives on `Supervisor` (`register_custom_runner` /
  `get_custom_runner`).
- Spec: `doc/schemas/runners.json` (`runner-id` type),
  `doc/website/src/spec/.../02-gl_call.rst` and `.../03-vm/05-permissions.rst`.
